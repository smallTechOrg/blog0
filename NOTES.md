# NOTES — harness-improvement journal

Not an app changelog. Each entry: symptom → action → lesson.

## 2026-10-12

- Run start 2026-10-12 15:19 local. Intake: 6 product rounds + technical round via AskUserQuestion, no tool failures. Lesson: design reference was a saved claude.ai artifact; the real app lived in a nested saved_resource.html script — root extracted it to spec/design/ for workers.
- Symptom: `.env` absent for the entire scaffold stage (user adding the key in parallel). Action: workers passed non-secret values inline per command; `check:openrouter` was run only to prove it fails closed, and key validation was handed back as PENDING. Lesson: the harness should treat "key arrives mid-build" as a normal state — gate steps that need the real key should be explicitly separable and re-runnable by the root.
- Symptom: `pnpm <script>` ran on Node 25 (pnpm installed under asdf's Node 25 from a parent `.tool-versions`) even though `.nvmrc` says 22. Action: scaffold pinned Node via `package.json` `devEngines.runtime` (onFail: download). Lesson: `.nvmrc`/`engines` alone don't pin the runtime pnpm uses; the scaffold gate should assert `pnpm exec node --version`.
- Symptom: spec required both `output: 'standalone'` and `start = next start`, so every `pnpm start` printed "next start does not work with output: standalone". Action: the setting moves to the Phase 5 Docker slice. Lesson: spec-writer should not adopt deploy-only build settings in the scaffold when they conflict with the documented local run command.
- Symptom: `.env` absent, so there was no admin password to seed for the Phase 1 gate. Action: the orchestrator generated a random one into gitignored `var/dev-admin.env` (mode 600), sourced by gate commands and never printed. Lesson: intake should collect (or generate) seed-admin credentials together with the API key.
- Symptom: the orchestrator fanned out wave A in the background, then ended its turn, so the root had to track the children. Action: the orchestrator now stays in control and waits for every child notification before handing back. Lesson: backgrounded fan-out is fine, but the orchestrator must not end its turn while children are running; say so explicitly in project-builder.md.
- Symptom: `next dev` (16.x) silently writes `AGENTS.md` at the repo root and re-creates it if deleted. Action: it is committed with Phase 1. Lesson: scaffold should expect framework-generated agent files and decide whether to commit or gitignore them up front.
- Symptom: a child generator booted a verification server on an ad-hoc port (3499) and returned without stopping it; qa-auditor found it orphaned. Action: the orchestrator killed it before commit. Lesson: give every child an explicit allowed port, and have the orchestrator run `lsof -ti tcp:<ports>` after each wave, not only at the end.
- Symptom: in Next 16.4, `notFound()` from a page segment server-renders the bare `__next_error__` page (404 status, chrome only after hydration), which conflicted with the spec's "no middleware/proxy" rule. Action: added a narrow `src/proxy.ts` on `/p/*` and amended the spec. Lesson: spec-writer should not ban framework primitives outright; state the constraint (auth is never done in middleware) instead.
- Symptom: with the key absent, qa-auditor must return BLOCKED (PENDING KEY) even when every non-key step is green. Action: committed the phase with the real-key steps marked PENDING KEY, skipping visibly, never mocked. Lesson: the verdict vocabulary needs a distinct "VERIFIED-PENDING-KEY" state so orchestrators don't conflate it with a code block.
- AskUserQuestion caps options at 4 per question, so per-feature gates have to be split across two questions.
- Symptom: a session-limit 429 killed the orchestrator mid-fan-out (all 7 Phase 2 children died within seconds of each other). Action: the root resumed via SendMessage from git state, and the orchestrator relaunched with smaller batches (≤4 concurrent children). Lesson: committing and pushing the spec + dependency changes BEFORE fan-out saved the work; always checkpoint to git before a wide fan-out, and cap concurrency when the provider limit is per session.
- Symptom: a Claude Code session restart mid-phase killed every child and process; partial, uncommitted wave work survived on disk. Action: checkpointed with typecheck and tests, committed the green WIP, and relaunched only the half-done slices with "finish this slice; these files already exist". Lesson: the orchestrator should commit green WIP after each slice lands, not only at phase end.
- Symptom: three concurrent Phase 3 slices each ran `pnpm test:integration` against the shared `blog0_test`, and every worker saw spurious FK/duplicate failures caused by the others truncating the schema. Action: the orchestrator ran the suite once, alone, before checkpointing (18/18 green). Lesson: tell per-slice generators to run only their own integration files, and reserve the full integration suite for the orchestrator/qa-auditor; or give each slice its own test DB (`blog0_test_<slice>`).
- Symptom: a second session-limit 429 hit mid-Phase 3 (S3.4, S3.5 and the wave-A audit all died). Action: resumed from git state; the WIP checkpoints again saved the work, and concurrency dropped to ≤2 children with small fixes done inline. Lesson: per-slice WIP commits are what make provider limits survivable.
- Symptom: a child's `pnpm build` overwrote `.next` while the root's `pnpm start` on :3410 was serving from it, so 3410 then returned 500 for its CSS chunks. Action: reported to the root for a restart. Lesson: when the root serves from the same checkout, gate builds need a separate `distDir` (e.g. `BLOG0_DIST_DIR=.next-gate`) or must run from a copy; the harness should make this the default.
- Symptom: the real-Jev seed-tldr integration test failed once in a full run, then passed alone and in the next full run (276/276). The error wasn't captured. Action: the orchestrator re-ran the suite with output saved to a log. Lesson: gate runs should always tee output to a file so a flaky live-provider failure can be diagnosed after the fact.
- Symptom: the user found manual tap-along Listen sync too cumbersome after Phase 3 shipped (a SPEC change: estimated timing replaced it, and tap-along code was deleted). Lesson: intake should have asked how much manual effort writers accept per article for sync; per-article effort budgets belong in the intake questions for any 'writer prepares X' feature.
